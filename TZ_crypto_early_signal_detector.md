# ТЗ: Crypto Early Signal Detector

## 1. Цель проекта

Разработать сервис (или агента на базе Claude Code), который автоматически отслеживает рынок криптовалют и находит монеты **на ранней стадии движения**, до того как рост станет заметен на графике цены. Система должна выявлять сигналы накопления (китов, деривативов, оттока с бирж, роста комиссий протокола) и присылать алерты с оценкой уверенности по каждому кандидату.

**Не входит в задачу:** торговые сигналы buy/sell, автоматическое исполнение сделок, финансовые рекомендации. Система только собирает и ранжирует кандидатов для ручной проверки.

---

## 2. Пользовательский сценарий

1. Система в фоне мониторит список монет (watchlist, 30-50 штук + опционально топ-300 по капитализации)
2. При срабатывании одного или нескольких сигналов (см. раздел 4) монета попадает в отчёт
3. Раз в день (или по расписанию) пользователь получает сводку: список кандидатов, какие именно сигналы сработали, ссылки на источники
4. Пользователь вручную решает, копать дальше или нет
5. Опционально: ручная пометка "отработало / не отработало" для последующей калибровки весов сигналов

## 3. Источники данных

| Источник | Что берём | Тип доступа |
|---|---|---|
| Coinglass | Open Interest, объём фьючерсов, ликвидации, funding rate | API (есть бесплатный тир с лимитами) |
| DeFiLlama | Fees, revenue, TVL по протоколам | Открытый API, без ключа |
| CoinGecko / CoinMarketCap | Цена, объём, капитализация, % роста за 24ч/7д/30д | API (free tier с лимитами запросов) |
| Nansen | Smart money flows, биржевые балансы, whale wallets | Платный API — уточнить бюджет, может быть заменён на бесплатные альтернативы (Arkham, Etherscan whale alerts) |
| Governance форумы проектов (Snapshot, Discourse, Forum.xxx) | Голосования, апгрейды, даты активации | Скрейпинг / RSS, у части есть API |
| Twitter/X, новостные агрегаторы | Заявки на ETF, анонсы листингов | API X (платный) или альтернативные агрегаторы новостей |

**Открытый вопрос:** нужен ли платный доступ к Nansen с самого начала, или на MVP заменить его связкой Etherscan/Arkham + ручным списком отслеживаемых кошельков.

## 4. Детектируемые сигналы (ядро системы)

Каждый сигнал — отдельный модуль с собственным весом. Итоговый скор монеты = сумма сработавших сигналов с учётом веса.

### 4.1 Дивергенция Open Interest / цена
- **Условие:** OI вырос на X% за 24-48ч, цена изменилась менее чем на Y%
- **Параметры (настраиваемые):** X = 30%, Y = 5% (стартовые значения, требуют калибровки)
- **Источник:** Coinglass

### 4.2 Отток монеты с бирж
- **Условие:** биржевые балансы падают N дней подряд при стабильном/растущем объёме
- **Источник:** Nansen / Arkham / on-chain данные биржевых кошельков

### 4.3 Активность смарт-мани / китов
- **Условие:** рост числа кошельков-китов ИЛИ рост суммарного холдинга у существующих китов, особенно на фоне падающего или бокового рынка в целом
- **Источник:** Nansen labelled wallets

### 4.4 Календарь катализаторов
- **Условие:** приближается известное событие (голосование, апгрейд, дедлайн заявки на ETF) в ближайшие 7-30 дней
- **Источник:** ручной / полуавтоматический сбор из блогов проектов, governance-форумов, CMC Events
- **Важно:** это единственный сигнал, требующий базы знаний с датами, которую нужно наполнять и поддерживать

### 4.5 Рост revenue/fees протокола без реакции цены
- **Условие:** fees/revenue протокола выросли на X% за 7-30 дней, капитализация токена не отреагировала (рост капы меньше роста revenue)
- **Источник:** DeFiLlama

### 4.6 Секторная ротация (лаг-эффект)
- **Условие:** монета А из сектора уже показала рост >20% за 7 дней, остальные монеты того же сектора (тег/категория) ещё не отреагировали
- **Источник:** CoinGecko categories + собственная классификация секторов

### 4.7 Пробой уровня на объёме
- **Условие:** цена пробивает многомесячный уровень сопротивления, объём в 2-3x выше среднего за последние 30 дней
- **Источник:** ценовые данные CoinGecko/биржевые API + технический анализ (можно через TA-Lib)

## 5. Архитектура (предложение для реализации через Claude Code)

```
/crypto-signal-agent
├── /collectors          # модули сбора данных с каждого источника
│   ├── coinglass.py
│   ├── defillama.py
│   ├── coingecko.py
│   ├── nansen.py
│   └── events_calendar.py   # ручная/полуручная база катализаторов
├── /signals              # детекторы сигналов (раздел 4), каждый - независимая функция
│   ├── oi_divergence.py
│   ├── exchange_outflow.py
│   ├── whale_activity.py
│   ├── catalyst_calendar.py
│   ├── revenue_price_gap.py
│   ├── sector_rotation.py
│   └── volume_breakout.py
├── /scoring
│   └── ranker.py          # агрегация сигналов в единый скор, ранжирование кандидатов
├── /storage
│   └── db.sqlite (или Postgres)  # история сигналов, монеты, результаты для калибровки
├── /notifications
│   └── telegram_bot.py     # ежедневная сводка + мгновенные алерты по порогу скора
├── /web                    # локальный веб-интерфейс
│   ├── backend/            # FastAPI
│   └── frontend/           # React — список кандидатов, история сигналов, ручная разметка, настройки весов/watchlist
├── config.yaml             # watchlist, пороги, веса сигналов, расписание
└── main.py                 # оркестратор, запускается по cron / Claude Code scheduled task
```

**Режим работы:** периодический опрос (cron / планировщик на локальном ПК, например каждые 4-6 часов для быстрых сигналов типа OI, раз в сутки для медленных типа revenue/fees) + агрегированный дневной отчёт в Telegram + постоянно доступный веб-дашборд.

## 6. Функциональные требования

1. Система должна поддерживать watchlist монет, редактируемый пользователем (файл конфига или простой интерфейс)
2. Каждый сигнал должен логироваться отдельно с таймстампом, значением метрики и источником
3. Скоринг должен быть прозрачным: пользователь видит, ЗА ЧТО монета получила скор, а не чёрный ящик
4. Веса сигналов должны быть настраиваемыми (config, не hardcode)
5. Должна быть возможность отметить результат сигнала постфактум ("сработало"/"не сработало") для последующего анализа точности
6. Уведомления: минимум Telegram-бот или email-дайджест раз в день
7. История всех сработавших сигналов должна сохраняться для последующего бэктеста

---

## 7. Нефункциональные требования

- Устойчивость к rate limits источников данных (retry с backoff, кэширование)
- Работа в рамках бесплатных/недорогих тиров API на MVP-этапе
- Логирование ошибок сборщиков данных (если источник недоступен — не молчать, а фиксировать)
- Расширяемость: добавление нового сигнала не должно требовать переписывания ядра

---

## 8. MVP vs следующие итерации

**MVP (первая версия):**
- 3 сигнала: OI-дивергенция, рост revenue без реакции цены, пробой на объёме (все три через бесплатные API — Coinglass free tier, DeFiLlama, CoinGecko)
- Watchlist из 20-30 монет вручную
- Ежедневная сводка в Telegram
- Хранение истории в SQLite

**Итерация 2:**
- Подключение Nansen (whale activity, exchange outflow) — требует бюджета
- Календарь катализаторов с полуручным наполнением
- Секторная ротация

**Итерация 3:**
- Автоматическая калибровка весов на основе истории "сработало/не сработало"
- Backtest-модуль: проверка сигналов на исторических данных

---

## 9. Риски и ограничения

- **Ложные срабатывания:** большинство сигналов будут давать шум, особенно на низколиквидных монетах — нужна ручная валидация, не автоматизировать решения
- **Лимиты API:** бесплатные тиры Coinglass/Nansen сильно ограничены по частоте запросов, это определяет частоту опроса
- **Календарь катализаторов** — самый трудоёмкий модуль, полностью автоматизировать сложно, скорее всего первое время потребует ручного пополнения раз в неделю
- **Не является финансовым советом** — система только для сбора информации, решения принимает пользователь

---

## 10. Решения по MVP

- **Источники данных на MVP: только бесплатные.** Nansen и X API откладываются до итерации 2. Whale activity и exchange outflow на старте не реализуем — либо заменяем бесплатной альтернативой (Arkham free tier, публичные Etherscan whale-алерты), либо просто выпиливаем из MVP и добавляем на итерации 2.
- Соответственно MVP-набор сигналов из раздела 8 (OI-дивергенция, revenue-gap, пробой на объёме) остаётся без изменений — все три уже строились на бесплатных API.
- **Уведомления: Telegram-бот.** Ежедневная сводка + опционально мгновенный алерт при сильном сигнале (настраивается порогом скора).
- **Веб-интерфейс: нужен, FastAPI + React.** Осознанный выбор в пользу задела на будущее вместо скорости Streamlit — список кандидатов, история сигналов, ручная разметка "сработало/не сработало", настройка весов и watchlist без правки конфига руками.
- **Хостинг: локальный ПК пользователя.** Планировщик — cron (Linux/macOS) или Task Scheduler (Windows), либо простой Python-скрипт с `schedule`/`APScheduler`, запущенный как фоновый процесс. Мониторинг работает, пока включён ПК — простой в выключенное время некритичен, отдельного решения под 24/7 (перенос на VPS) не требуется.
