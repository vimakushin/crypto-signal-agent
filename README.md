# crypto-signal-agent

Crypto Early Signal Detector — см. `TZ_crypto_early_signal_detector.md`.

## Статус

MVP в процессе (раздел 8 ТЗ). Готово:

- Структура проекта (`collectors/`, `signals/`, `scoring/`, `storage/`, `notifications/`, `web/`)
- Python 3.12 + venv (`.venv`)
- Сборщик DeFiLlama (`collectors/defillama.py`) — fees/revenue и market cap по watchlist из `config.yaml`
- Сборщик Binance Futures (`collectors/binance_futures.py`) — история Open Interest и цены по watchlist фьючерсов из `config.yaml` (без API-ключа; заменяет Coinglass — см. комментарий в файле)
- Сборщик CoinGecko (`collectors/coingecko.py`) — дневная история цены/капитализации/объёма по одной монете (используется скриптом backfill ниже и ежедневным циклом `--cycle defillama` для сигнала "пробой на объёме")
- Хранилище истории в SQLite (`storage/db.py`, `storage/db.sqlite`)
- Сигнал revenue-gap (`signals/revenue_price_gap.py`, раздел 4.5 ТЗ)
- Сигнал OI-дивергенция (`signals/oi_divergence.py`, раздел 4.1 ТЗ)
- Сигнал "пробой уровня на объёме" (`signals/volume_breakout.py`, раздел 4.7 ТЗ) — тот же watchlist и цикл, что и revenue-gap (`--cycle defillama`), т.к. источник (CoinGecko) тоже отдаёт дневные данные
- Точка входа `main.py` — поддерживает `--cycle {all,defillama,binance}` (по умолчанию `all`, для ручного запуска); при `all` выполняет оба независимых цикла, ошибка в одном источнике не мешает второму отработать
- Скрипт разового наполнения истории задним числом — `scripts\backfill_history.py` (подробнее ниже)
- Расписание разделено на два отдельных задания Планировщика Windows (подробнее ниже)

Ещё не сделано: ranker/scoring, Telegram-уведомления, веб-интерфейс.

## Запуск

```powershell
.venv\Scripts\python.exe main.py
```

По умолчанию (без `--cycle`) выполняются оба цикла сразу. Первый запуск сохраняет снимки по обоим циклам, но кандидатов, скорее всего, не найдёт: сигналу revenue-gap нужно минимум 7 дней накопленной истории капитализации в SQLite, чтобы было с чем сравнивать, а сигналу "пробой на объёме" — почти полное окно `resistance_lookback_days` (по умолчанию 180 дней) и `volume_avg_lookback_days` (30 дней) цены/объёма — без `scripts\backfill_history.py` (см. ниже) это накопится только через несколько месяцев ежедневных запусков. Сигнал OI-дивергенция может сработать уже на первом запуске — коллектор Binance Futures отдаёт сразу до ~36-48 часов истории за один вызов, а не только "сейчас". Чтобы прогнать только один цикл вручную:

```powershell
.venv\Scripts\python.exe main.py --cycle defillama
.venv\Scripts\python.exe main.py --cycle binance
```

## Наполнение истории задним числом (`scripts\backfill_history.py`)

Обычный ежедневный/шестичасовой запуск копит историю только с момента, когда впервые заработал `main.py`. Чтобы сигналам было на чём проверяться сразу, а не спустя недели, есть отдельный разовый скрипт, который загружает историю из прошлого:

- **DeFiLlama + CoinGecko**: для каждого протокола из `watchlist.defillama_protocols` — вся доступная история revenue (обычно несколько лет, по дням) плюс история цены/объёма/капитализации с CoinGecko (доступно максимум 365 дней — таково ограничение бесплатного тарифа CoinGecko) и пересчёт `revenue_total_7d/30d` и `revenue_change_7d/30d_pct` за каждую историческую дату **тем же способом**, каким это делает сам DeFiLlama в текущем ежедневном сборщике — чтобы старые и новые строки в базе были сравнимы между собой. Последние ~3 дня истории скрипт намеренно не трогает — их и так покрывает обычный ежедневный сборщик, а формат отметки времени у них разный (у backfill — полночь UTC исторической даты, у живого сборщика — реальное время запуска), поэтому эти дни не подстраховать одной лишь проверкой на дубли в базе.
- **Binance Futures**: у самого Binance глубина истории Open Interest физически ограничена ~30 днями независимо от размера окна запроса — глубже эти данные взять неоткуда, это не ошибка и не искусственное ограничение.

Запуск (один раз, вручную — это медленная операция из-за лимитов CoinGecko, не часть ежедневного цикла):

```powershell
.venv\Scripts\python.exe scripts\backfill_history.py
```

Скрипт безопасно перезапускаемый: если он упал на середине (например, CoinGecko временно ограничил частоту запросов), повторный запуск не создаст дублей в базе — уже сохранённые дни просто будут пропущены и он продолжит с того места, где остановился. Прогресс и все пропуски (не хватает истории, источник недоступен, "грязное" (NaN/бесконечное) значение revenue или цены/объёма от источника) видны в `logs\backfill.log`.

Ежедневный цикл `main.py --cycle defillama` берёт `gecko_id` для каждого протокола из ответа `/protocols` DeFiLlama, который он и так уже запрашивает ради капитализации — то есть без лишнего запроса. Проверено вживую: реальный запрос к `/protocols` вернул `gecko_id` для всех 25/25 протоколов текущего watchlist, так что для них история цены/объёма собирается штатно. Если когда-нибудь в лог попадут строки `no gecko_id on file for` по протоколу, у которого `gecko_id` точно есть (например `lido`, `aave-v2`) — значит DeFiLlama перестала отдавать это поле для конкретного протокола, и тогда нужен запасной вариант: брать `gecko_id` из `fetch_protocol_daily_revenue_history()`, как это уже делает `backfill_history.py`.

## Автоматический запуск по расписанию (Планировщик заданий Windows)

История копится сама с помощью **двух отдельных заданий** Планировщика Windows — расписание раздельное, потому что revenue/fees (DeFiLlama) обновляется медленно и его достаточно проверять раз в сутки, а Open Interest (Binance) — быстрый сигнал, ТЗ требует опрашивать его каждые несколько часов:

- **`CryptoSignalAgent-DeFiLlama`** — раз в сутки, `main.py --cycle defillama`.
- **`CryptoSignalAgent-BinanceOI`** — каждые несколько часов, `main.py --cycle binance`.

(Оригинальное единое ежедневное задание было проверено вручную ранее; после разделения на два задания по плану их тоже нужно проверить так же — командами ниже.)

Время/периодичность задаются не в скрипте, а в `config.yaml`:
- `schedule.defillama_run_time` (по умолчанию `08:00`) — время ежедневного запуска DeFiLlama-задания;
- `schedule.binance_futures_poll_hours` (по умолчанию `6`) — как часто в течение суток запускается Binance-задание.

Чтобы поменять любое из этих значений, отредактируйте `config.yaml` и один раз заново выполните `scripts\register_scheduled_task.ps1` (команда — ниже), в PowerShell лезть не нужно.

Если компьютер в назначенное время выключен или спит — конкретный запуск в этот раз не выполнится (это ожидаемое ограничение MVP, см. раздел про хостинг в ТЗ); при следующем включении компьютера Планировщик попробует запустить пропущенное задание как можно скорее.

Как проверить, что задания есть и когда они в последний раз срабатывали:

```powershell
Get-ScheduledTask -TaskName "CryptoSignalAgent-DeFiLlama" | Get-ScheduledTaskInfo
Get-ScheduledTask -TaskName "CryptoSignalAgent-BinanceOI" | Get-ScheduledTaskInfo
```

Запустить любое прямо сейчас вручную (для проверки, не дожидаясь расписания):

```powershell
Start-ScheduledTask -TaskName "CryptoSignalAgent-DeFiLlama"
Start-ScheduledTask -TaskName "CryptoSignalAgent-BinanceOI"
```

Куда смотреть лог (что программа сделала при каждом запуске, включая ошибки, если какой-то источник данных был недоступен):

- `logs\scheduler_defillama.log` — задание `CryptoSignalAgent-DeFiLlama` (`main.py --cycle defillama`).
- `logs\scheduler_binance.log` — задание `CryptoSignalAgent-BinanceOI` (`main.py --cycle binance`).
- `logs\scheduler.log` — только ручной запуск `main.py` без `--cycle` (оба цикла сразу, в одном процессе).

Раньше был один общий файл на оба задания — пришлось развести по разным файлам: задания `CryptoSignalAgent-DeFiLlama` и `CryptoSignalAgent-BinanceOI` — это два независимых процесса Windows, они могут реально сработать одновременно (не только если запустить их вручную одно за другим для проверки, но и если, например, ежедневное время DeFiLlama когда-нибудь совпадёт с одним из тиков Binance), а два процесса, пишущие в один и тот же файл лога одновременно, физически могут "разорвать" строки друг друга — это не гипотетическая проблема, а воспроизведённая вживую при проверке. У разового скрипта `backfill_history.py` — свой отдельный лог, `logs\backfill.log`.

Лог всегда объясняет, ЗА ЧТО монета получила сигнал (значение метрики, порог, реально прошедшее время между сравниваемыми точками — а не просто настройка из конфига, если в истории были пропуски данных), а строка про «кандидатов не найдено» отдельно различает две разные причины: «истории пока недостаточно» (рано делать вывод) и «данных хватает, но порог никто не пробил» (рынок сейчас спокойный). Если сбор данных Binance Futures или CoinGecko (для сигнала "пробой на объёме") в конкретный день полностью не удался, лог явно предупредит об этом отдельной строкой, вместо того чтобы молча оценивать сигнал по устаревшим данным из прошлого запуска.

Если задания пропали (например, после переустановки Windows или переноса проекта на другой компьютер), пересоздать оба можно тем же скриптом, которым они были созданы (он же автоматически уберёт старое единое задание `CryptoSignalAgent-DailyRun`, если оно осталось от версии проекта до разделения расписания):

```powershell
powershell -ExecutionPolicy Bypass -File scripts\register_scheduled_task.ps1
```

## Резервные копии базы данных (`scripts\backup_db.py`)

`storage\db.sqlite` — это вся накопленная история (снимки DeFiLlama, Binance, CoinGecko за месяцы работы), и в git она не попадает (см. `.gitignore`) — файл базы данных слишком большой и постоянно меняется, версионировать его бессмысленно. Чтобы эту историю не потерять, есть отдельный скрипт бэкапа.

Важная техническая деталь: обычное копирование файла (через проводник Windows или команду копирования) в момент, когда программа как раз дописывает в базу данные (а это может происходить в любой момент — см. раздел про Планировщик выше), может скопировать файл "недописанным" и повредить резервную копию. Скрипт `scripts\backup_db.py` использует официальный, безопасный способ SQLite снять копию "на лету" (`sqlite3.Connection.backup`), который не ломается, даже если в этот момент кто-то пишет в базу.

Запуск вручную:

```powershell
.venv\Scripts\python.exe scripts\backup_db.py
```

Куда сохраняются копии — по умолчанию в папку `backups\` внутри проекта (она НЕ входит в git, см. `.gitignore`). У этого варианта есть два по-разному надёжных места хранения — выберите, что вам удобнее:

1. **Папка `backups\` внутри проекта (по умолчанию, ничего настраивать не нужно).** Самый простой вариант для начала. Минус: копии лежат на том же диске, что и сам проект — если этот диск/компьютер выйдет из строя или будет утерян, пропадут и оригинал, и резервные копии одновременно.
2. **Папка внутри уже настроенной у вас облачной синхронизации** (например, OneDrive или Google Диск, если они у вас установлены и работают на этом компьютере). Тогда копии автоматически попадут ещё и в облако, и это защищает даже от поломки всего компьютера. Пример запуска с такой папкой:

```powershell
.venv\Scripts\python.exe scripts\backup_db.py --backup-dir "C:\Users\vital\OneDrive\crypto-signal-agent-backups"
```

Скрипт сам не умеет проверить, есть ли у вас OneDrive или Google Диск — это решение остаётся за вами.

Хранятся только последние 14 резервных копий (это можно изменить параметром `--keep`), более старые удаляются автоматически, чтобы место на диске не кончилось. Каждая копия — отдельный файл с датой и временем в названии (например `db_20260909_080000.sqlite`), поэтому копии никогда не перезатирают друг друга.

Лог работы скрипта — `logs\backup.log` (что скопировано, что удалено при ротации, и любые ошибки — например, если диск переполнен или папка для копий недоступна).

Бэкап подключён к Планировщику Windows — так же, как два других задания выше, он делается третьим заданием, **`CryptoSignalAgent-Backup`**, которое раз в сутки само запускает `scripts\backup_db.py` (с настройками по умолчанию — папка `backups\` внутри проекта и хранение последних 14 копий). Время запуска задаётся в `config.yaml`:

- `schedule.backup_run_time` (по умолчанию `09:00`) — на час позже времени DeFiLlama-задания (`08:00`), чтобы дневной снимок DeFiLlama к этому моменту уже был в базе; жёсткой привязки к нему нет, время выбрано просто как спокойный утренний момент.

Чтобы поменять время, отредактируйте `config.yaml` и один раз заново выполните `scripts\register_scheduled_task.ps1` — ту же команду, что и для двух других заданий (см. раздел выше); она пересоздаёт все три задания сразу.

Проверить, что задание есть и когда оно в последний раз срабатывало:

```powershell
Get-ScheduledTask -TaskName "CryptoSignalAgent-Backup" | Get-ScheduledTaskInfo
```

Запустить прямо сейчас вручную (для проверки, не дожидаясь расписания):

```powershell
Start-ScheduledTask -TaskName "CryptoSignalAgent-Backup"
```

Как и у двух других заданий, если компьютер в назначенное время выключен или спит — этот конкретный запуск в этот раз не выполнится, при следующем включении Планировщик попробует запустить пропущенное задание как можно скорее.

## Контроль версий (git) — как сохранять изменения и восстановить проект

Простыми словами: git — это "история изменений" проекта. Каждое сохранение ("коммит") — это как снимок всех файлов на момент времени, к которому потом всегда можно вернуться. Это касается только кода (`.py`, `.yaml`, `.md` и т.п.) — база данных, логи и резервные копии в git не попадают (см. `.gitignore`), для них есть отдельный бэкап (раздел выше).

### Как сохранить изменения ("закоммитить")

Делать это стоит не после каждой мелкой правки, а после того, как ассистент что-то поменял в коде и результат вас устроил — то есть законченный, проверенный кусок работы.

```powershell
git add .
git commit -m "краткое описание того, что изменилось"
git push
```

Что делает каждая команда:
- `git add .` — отмечает все изменённые/новые файлы как "готовые к сохранению" (пока ничего ещё не сохранено).
- `git commit -m "..."` — собственно сохраняет снимок этих файлов в историю проекта, с вашим коротким пояснением, что именно поменялось. Это уже происходит только у вас на компьютере.
- `git push` — отправляет сохранённые снимки на GitHub (или другой удалённый сервер), где они хранятся отдельно от вашего компьютера — это и есть защита на случай, если что-то случится с самим компьютером.

### Как восстановить проект с нуля на новом компьютере

Что должно быть установлено заранее: Python 3.11+ и git.

```powershell
git clone https://github.com/vimakushin/crypto-signal-agent.git
cd crypto-signal-agent
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
```

После этого код и настройки (`config.yaml`) на месте, но:

- **История в базе данных будет пустой** — её нужно восстановить отдельно, из резервной копии (раздел выше, копии лежат в `backups\` или в вашей облачной папке — смотря что вы выбрали). Восстановление — это просто копирование файла копии на место основной базы данных:

```powershell
copy "backups\db_20260909_080000.sqlite" "storage\db.sqlite"
```

  (вместо `db_20260909_080000.sqlite` подставьте имя самой свежей копии, которая у вас есть).

- Секреты (если они когда-нибудь появятся — сейчас в проекте их нет, все используемые источники данных бесплатные и не требуют ключей) нужно будет заново положить в файл `.env` в корне проекта — он тоже не хранится в git.

- Задания Планировщика Windows на новом компьютере нужно зарегистрировать заново (см. раздел выше про `scripts\register_scheduled_task.ps1`), они не переносятся автоматически вместе с кодом.
